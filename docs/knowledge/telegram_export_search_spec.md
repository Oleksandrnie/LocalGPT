# ТЗ: HTML-выгрузки Telegram в существующем RAG

Статус: реализована базовая интеграция; свободные ответы LLM требуют отдельной live-проверки. Уточнение пользователя от 28 октября 2026 г. заменяет первоначальный сценарий отдельного инструмента поиска.

## Цель

Пользователь добавляет Telegram Desktop HTML в обычный RAG активного профиля и индексирует его текущим локальным хешевым механизмом. Затем задаёт вопросы в обычном чате: найти данные, уточнить даты, сузить запрос ключевыми словами. Ответ должен опираться на найденные сообщения с датой, автором и ID для ручного поиска в Telegram.

## Требования

1. Существующая загрузка RAG принимает `.md` и `.html`. HTML проверяется как Telegram Desktop export, произвольные веб-страницы отклоняются.
2. Парсер читает `.history > .message`, дату из `title` у `.date`, автора из `.from_name`, текст и ссылки, пересылки, ответы, признаки медиа. Автор наследуется у `joined` только в своей группе. Служебные блоки распознаются и не индексируются как авторские сообщения.
3. Полная дата сохраняется без придумывания часового пояса. Текст с датой, автором, названием чата и ID повторяется в каждой части длинного сообщения. HTML-разметка удаляется, переносы сохраняются, скрипты не выполняются, ссылки и ресурсы не загружаются.
4. Индексация использует существующий `local_hash` provider и существующие таблицы RAG. Отдельная база архивов, отдельный интерфейс поиска и новая embedding-модель не нужны.
5. Формат и provenance сообщения сохраняются в document/chunk metadata и передаются в текущий evidence-контекст чата.
6. Запросы с ISO-датами `2026-07-11`, датами `11.07.2026`, диапазоном двух дат или месяцем с годом (`за июль 2026`) фильтруют Telegram-фрагменты перед ранжированием. Дата текущего сообщения имеет приоритет перед датами из истории.
7. Короткие уточнения, запросы дат и ключевых слов сохраняют предыдущую тему через существующий механизм составления RAG-запроса. Ответы «за какие даты» извлекают даты из найденных сообщений.
8. Markdown, профили, изоляция session-owned источников, повторная индексация, удаление RAG-файлов и текущий Chat/RAG pipeline продолжают работать.
9. Индексирование/повторная индексация Telegram не отправляет текст внешнему provider. Для Telegram требуется local_hash и локальный endpoint chat-модели. При несовместимой настройке операция явно отклоняется до отправки текста.
10. Исходный файл пользователя не изменяется. Как и другие RAG-файлы, загруженная копия хранится в игнорируемом профильном `rag_sources`; оригинальные данные и персональные тексты не включаются в Git или тестовые фикстуры.

## Приёмка

- Приложенный пример: 173 блока, 146 обычных сообщений, 27 служебных; полная дата имеется у всех обычных сообщений. Проверяется локально без копирования текстов в репозиторий.
- Искусственные фикстуры проверяют даты, наследование автора, пересылки/ссылки, длинные сообщения, недопустимый HTML и ID.
- Сквозная проверка: HTML → RAG → local_hash → запрос → evidence с ID/датой/автором; затем уточнение даты/ключевых слов.
- Даты вне диапазона исключены, профиль B не получает документы профиля A; повторный ingest не создаёт дубликатов, удаление очищает индекс.
- Проверяется блокировка внешнего chat/embedding endpoint, включая повторную индексацию.
- Выполняются deterministic Python/Node регрессии. Live LLM smoke описывается отдельно; без него качество свободного ответа модели не считается подтверждённым.

## Ограничения и следующий этап

Для Telegram HTML нет фиксированного байтового предела; загрузка и разбор HTML работают потоком с освобождением разметки обработанных сообщений. Backend принимает до 12 файлов на HTTP-запрос; UI позволяет выбрать любое количество и отправляет последовательные партии с общим прогрессом. Реальные ограничения RAM/диска и модельного контекста сохраняются. Для Markdown сохраняются лимиты 5 MiB/файл и 20 MiB/загрузку. Страницы `messages2.html` загружаются как самостоятельные источники. Даты без года и неоднозначные естественные формулировки не трактуются как строгие фильтры. Поиск по общему RAG остаётся ограничен top_k/context budget и не гарантирует исчерпывающий аудит каждого сообщения. Хешевые векторы не являются семантическими embeddings; качество поиска опирается на текущий lexical/hybrid retrieval. Анализ медиа, автоудаление в Telegram, отдельный архивный UI и новая семантическая модель в эту доработку не входят.


Дополнение по проверке 29 октября: поддержаны открытые/отрицательные временные границы, нормализация написания хэштегов, изоляция совпадающих ID по явно указанному источнику и прямое извлечение полного текста по ID+запросу дословной цитаты. Подробности и пределы — в [RAG](rag.md).
