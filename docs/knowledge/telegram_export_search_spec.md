# ТЗ: локальный поиск по HTML-выгрузкам Telegram

**Статус:** черновик требований к доработке LocalGPT  
**Дата:** 28 октября 2026 г.  
**Цель:** импортировать Telegram Desktop HTML-выгрузку в LocalGPT, находить сообщения по содержанию и дате и помогать пользователю вручную находить их в Telegram для дальнейшей очистки.

## 1. Контекст проекта

LocalGPT уже содержит profile-scoped RAG для Markdown, SQLite, FastAPI mini-apps в `backend/apps/`, статический Web UI и работу с локальными моделями. Текущий RAG не разбирает HTML-выгрузки и не хранит отдельные авторские, временные и Telegram message ID поля. Поэтому поиск по экспорту нужно оформить как отдельную функцию с результатами на уровне сообщений. Не загружать выгрузку в общий RAG автоматически: это затруднит точную фильтрацию, проверку даты и переход от результата к исходному сообщению.

Функция использует выбранный профиль LocalGPT как границу владения данными. Импорт и базовый поиск должны работать без LLM, embeddings и доступа в Интернет. Семантический поиск и сводка — опциональные локальные дополнения.

## 2. Что показал пример

Локально изучен переданный файл `messages.html` (около 211 KiB). Это UTF-8 HTML с контейнером истории `.history`, заголовком чата и блоками `.message`.

В примере обнаружено:

- 173 блока: 146 обычных сообщений и 27 служебных событий;
- у 146 обычных сообщений есть полная дата-время в атрибуте `title` у `.date.details`; отображаемый текст даты может содержать только время и пометку `edited`;
- 97 обычных блоков имеют класс `joined`: автор (и иногда отображаемое время) вынесен в предыдущий блок группы и должен наследоваться при разборе;
- блок `.text` содержит текст и форматирование HTML; сообщения также могут содержать пересылки, ответы, ссылки и медиа-блоки;
- встречаются ID вида `message<ID>`, но не у каждого служебного блока.

Это наблюдения по одному примеру, а не исчерпывающее описание всех версий Telegram Export. Парсер обязан проверять ожидаемую структуру и сообщать о неизвестном формате, а не молча импортировать неверные данные.

## 3. Цель и сценарий пользователя

Пользователь выбирает HTML-файл или части одного Telegram-экспорта, импортирует архив в выбранный профиль, вводит запрос или фразу, сужает результат датами/автором и получает список точных исходных сообщений с датой, временем, ID и контекстом. По этим данным пользователь вручную находит и при необходимости удаляет сообщение в Telegram.

Функция не входит в аккаунт Telegram, не отправляет команды Telegram и не удаляет сообщения автоматически.

## 4. Границы первой версии

### Входит

- импорт Telegram Desktop HTML (`messages.html`, а также пронумерованных частей одной истории, если выбрано несколько файлов);
- предварительный просмотр распознанного архива до сохранения;
- хранение сообщений по отдельным архивам и профилям;
- поиск по словам и точным фразам, фильтры, сортировка, просмотр исходного контекста;
- экспорт найденных результатов в CSV/JSON;
- явное удаление импортированного индекса/архива из LocalGPT.

### Не входит

- автоматический вход в Telegram, получение экспорта или удаление сообщений через Telegram API/клиент;
- поиск и анализ содержимого медиафайлов, распознавание аудио/видео или OCR изображений;
- синхронизация изменений из Telegram после экспорта;
- автоматический перенос каждого сообщения в общий RAG;
- передача HTML, текста или запросов во внешний AI/API.

Медиа и ссылки показываются как метаданные, если они присутствуют в HTML. Их содержимое не открывается и не скачивается автоматически.

## 5. Функциональные требования

### 5.1 Импорт и предварительный просмотр

1. UI позволяет выбрать один HTML-файл либо несколько пронумерованных страниц одного экспорта.
2. До сохранения показываются: название чата, количество файлов, количество обычных сообщений и служебных событий, диапазон дат, количество сообщений без текста/автора/ID, дубликаты ID и предупреждения парсера.
3. Если несколько страниц содержат разные названия чата или не подходят по шаблону экспорта, импорт останавливается с понятной ошибкой.
4. Повторный импорт того же набора файлов распознаётся по хэшу и предлагает открыть уже существующий архив, заменить его либо отменить операцию. Нельзя незаметно создавать дубликат.
5. Импорт не изменяет выбранные исходные HTML-файлы. После разбора временные upload-файлы удаляются.
6. Служебные блоки учитываются отдельно и по умолчанию скрыты в поиске; пользователь может включить их фильтром.

### 5.2 Разбор сообщения

Для каждого блока хранить как минимум:

- ID сообщения из HTML без префикса `message` и исходное значение ID;
- порядковый номер блока в экспорте — в том числе для блоков без ID;
- точное исходное значение даты-времени из `title` и нормализованную дату-время для фильтрации/сортировки;
- имя автора; для блока `joined` корректно наследовать автора предыдущего сообщения той же группы;
- текст без HTML-разметки с сохранением абзацев и переносов;
- ссылки из тела сообщения, имя автора пересылки, сведения об ответе/цитате, наличие медиа и тип блока, если эти поля присутствуют;
- тип блока: обычное сообщение или служебное событие.

Наследование автора/времени сбрасывается на границе группы, нового дня или служебного события согласно структуре экспорта. Нельзя приписывать значение предыдущего автора к независимому следующему сообщению.

В UI показывать исходное время как оно дано экспортом. В выгрузке примера нет временной зоны/UTC offset, поэтому не выполнять недоказанное преобразование и явно отметить, что время — значение из экспорта.

### 5.3 Поиск

- Базовый режим — локальный поиск по всем сообщениям архива: слова, фраза в кавычках, фильтр автора, диапазон дат, наличие пересылки/ссылки/медиа и включение служебных событий.
- Поиск работает по русскому и английскому тексту, включая `ё/е`, регистр и пунктуацию. Условия поиска подсвечиваются в найденном фрагменте.
- Результаты сортируются по дате и порядку сообщений; пользователь может переключить сортировку на обратную хронологию.
- Пустой запрос не должен сканировать и показывать содержимое всего архива без фильтра или явного действия пользователя.
- Семантический поиск по запросам вроде «где договорились о сроках» допустим как отдельный режим только при доступной локальной embedding-модели. Он не заменяет точный поиск и помечается в UI как семантический.
- Если локальная модель не настроена, импорт, ключевые слова, фразы и фильтры продолжают работать. Не подменять ошибку модели пустым результатом.
- Опциональная AI-сводка результатов может использовать только локальную модель, только по явному действию пользователя и должна сопровождаться ссылками на сообщения-источники. Базовый поиск и отображение результата не зависят от сводки.

### 5.4 Представление результата

Каждый результат должен содержать:

- дату и время из экспорта;
- автора (в том числе у `joined`-сообщений);
- исходный Telegram message ID, если он есть;
- совпавший текст с подсветкой; раскрываемый полный текст;
- пометки «переслано», «ответ», «есть медиа/ссылка» при наличии;
- соседние сообщения в исходном порядке по действию пользователя, чтобы восстановить контекст;
- название архива/чата.

Не обещать прямой переход в конкретное сообщение Telegram: ID и HTML-экспорт помогают искать, но формат экспорта не гарантирует ссылку, принимаемую Telegram-клиентом. Информация должна быть достаточной для ручной проверки.

Экспорт CSV/JSON содержит поля результата и исходный архивный ID. CSV корректно экранирует переносы строк, кавычки и запятую/разделитель.

## 6. Локальность и безопасность данных

1. Импорт, хранение, индексирование и обычный поиск выполняются на устройстве LocalGPT; сеть для них не нужна.
2. Новые endpoint-ы этой функции доступны только с loopback-интерфейса. Если приложение запущено в LAN-режиме и не может ограничить эту функцию loopback-ом, функция должна быть отключена в таком режиме.
3. Парсер не выполняет скрипты из HTML, не загружает его CSS/картинки/ссылки и не разрешает внешние URL. Текст из файла отображается как экранированные данные, а не как HTML/инструкции.
4. Даже если в LocalGPT настроен внешний OpenAI-compatible provider, Telegram-функция не отправляет ему текст, запросы, embeddings или сводки. Семантический поиск/сводка включаются только через явно выбранный локальный provider и проверенный loopback endpoint; при невозможности подтвердить локальность функция недоступна с понятным сообщением.
5. По умолчанию в LocalGPT сохраняется разобранный индекс и минимальные метаданные источника (имя файла, название архива, хэш, время импорта), а не копия оригинального HTML или медиа. Абсолютный путь исходного файла не сохранять.
6. Удаление архива очищает его сообщения, индексы и локальные производные данные, но не исходную выгрузку. Удаление профиля должно очищать все принадлежащие ему архивы.
7. Учитывать существующее ограничение проекта: локальная SQLite-база не зашифрована на диске. Не заявлять шифрование at rest.

## 7. Предлагаемая интеграция в код проекта

- Отдельная feature-папка `backend/apps/telegram_search/` с parser, service, schemas и router по текущим границам mini-app.
- Подключение router в `backend/server.py`.
- Отдельные SQLite records/migrations для архива и сообщений с `profile_id`, внешним ключом, порядковым номером и индексами по дате/автору. Поля Telegram нельзя терять при разбиении текста на RAG chunks.
- Для точного поиска предусмотреть индекс полнотекстового поиска SQLite (например, FTS5 после проверки доступности в runtime) и корректный fallback, если модуль недоступен. Фильтры даты/автора должны применяться к каждому сообщению до ранжирования.
- UI разместить отдельным экраном/инструментом в стиле существующего Web UI. Доступ к архиву всегда ограничен активным профилем.
- Повторно использовать только внутренние локальные сервисы embeddings/model selection при реализации необязательного семантического режима; не обходить их прямым сетевым вызовом к произвольному endpoint.
- Не складывать текст экспорта в обычный чат или общий RAG автоматически.

## 8. Приёмочные критерии

1. На приложенном примере импорт распознаёт название чата из HTML и 173 блока, включая 146 обычных сообщений и 27 служебных событий; предупреждения и детали отсутствующих полей показаны в предварительном просмотре.
2. Для сообщения с HTML ID вида `message<ID>` сохраняются исходный ID, полное время из `title` и текст соответствующего сообщения.
3. Запрос по уникальной фразе находит верный блок; поиск по автору/дате корректно включает сообщения `joined` с унаследованным автором и сортирует по полной дате-времени.
4. Включение служебных событий меняет набор результатов явно; по умолчанию служебные блоки не смешиваются с обычными сообщениями.
5. Результат можно проверить по исходному тексту, ID, времени, автору и соседним сообщениям; экспорт в CSV/JSON сохраняет эти поля.
6. Перезагрузка LocalGPT сохраняет архив и выдаёт те же результаты. Удаление архива удаляет только индекс LocalGPT; исходный HTML остаётся нетронутым.
7. Два профиля не видят архивы друг друга; при удалении профиля очищаются связанные архивы.
8. Парсер корректно сообщает о повреждённом/неподдерживаемом HTML, неоднозначной дате, повторяющихся ID и неверно выбранных частях экспорта; не создаёт частичный «успешный» индекс без отчёта.
9. При отключённой сети успешно выполняются импорт, точный поиск, фильтры и экспорт. Ни один из этих сценариев не требует модели.
10. В LAN-режиме с другого устройства нельзя получить или искать Telegram-архив; удалённые provider-ы не вызываются.
11. Обезличенные тестовые фикстуры повторяют структуру выгрузки, включая `joined`, `service`, пересылки, ответы, ссылки и media-блоки. Исходные тексты и персональные данные приложенного HTML не копируются в репозиторий.

## 9. Готовность к реализации

Перед началом реализации уточнить только продуктовые решения, которые нельзя вывести из проекта:

1. Нужна ли в первой версии семантическая модель/AI-сводка или достаточно точного и фильтруемого поиска?
2. Нужно ли сохранять исходный HTML в LocalGPT (по умолчанию ТЗ предусматривает не сохранять)?
3. Какой верхний размер выгрузки и ожидаемое число сообщений нужно поддержать на целевом компьютере?

До получения ответов безопасный MVP — локальный импорт одной/нескольких страниц, точный поиск, фильтры, контекст сообщений и экспорт результатов; семантический режим остаётся отдельным необязательным этапом.
